# 采集过程与客户进展

这是四仓销售工作流之后的 Leadsgen 增量。服务器是否已部署，以
[infra 发布记录](https://github.com/niuroumiantt/infra/blob/main/docs/handoff/leadsgen-progress-release-2026-10-02.md) 为准。
本批没有自动发现网站、定时搜索或新增发信动作。

## 在哪里查看

- **采集任务 → 采集工作台**：候选、成功、失败和待处理数量；官网采集与邮件同步各自的心跳；候选最近更新时间；展开批次后查看具体网站和执行过程。手机使用可展开卡片。
- **查看过程**：每次尝试的开始、结束、已读页数、robots 检查、页面响应、提取数量与失败原因。新版本区分新增来源与更新已有来源；旧批次只显示已有结果快照，不编造逐页历史。
- **线索总览 → 详情 → 客户进展与下一步**：负责人更新阶段、行动状态、日期和依据。总览可筛选“待安排下一步”与“跟进逾期”。
- **详情 → 进展时间线**：客户来源、采集、邮件事件、交接、企业关联、人工进展；保留修改前后内容、操作人和时间，按入库顺序分页。可手动刷新历史。
- **详情 → 企业档案**：企业编号、原来源编号和当前有权限查看的同企业来源。管理员核对法律名称、官网或客户确认后，可关联/取消关联；不会扩大任何人的访问权限。

## 搜索方式、间隔与重试

目前按管理员提交的官网名单采集，每批 1–30 个；没有搜索引擎查询和定时增量发现。
后台每 5 秒检查队列；同站请求至少间隔 3 秒并遵守 robots 要求。每站最多检查 8 个候选页面；
找到联系方式后最多解析 2 页，否则最多 4 页；90 秒是循环预算而非整个网络过程的硬超时。
网页大小上限 2 MB；DNS 固定连接与公开地址检查、同源约束保持。

暂时性网络、DNS、请求超时和 robots 服务故障，可由管理员点击“60 秒后重试”。
原失败尝试保留；新版本每候选最多三次正式尝试，旧版本只有快照的尝试编号为 0。
同一失败的重复提交返回 409；排队 60 秒前不会执行。重试只有主动点击才创建，升级不会重试已有失败。
服务重启保留中断尝试，并继续原来的待处理任务；旧执行的迟到结果不能覆盖新尝试。

拒绝访问、限流、证书、页面大小、跨源跳转及旧版含糊的 robots 错误须先核验。
“核验网址并建新任务”只预填原网址，由管理员修正后提交，不自动绕过站点规则。
只记录 URL、状态、页数和数量等过程信息，不在过程日志中存网页全文或凭据。

网站采集和邮件集成使用独立工作线程，SQLite 每次操作独立连接。单个网站慢不再占住邮件同步循环；
生产仍运行单个应用实例，不能横向增加多个采集进程共用同一数据库。

## 一家公司与多次机会

`company_id` 是企业关联标识；原来的 `account.id` 保持为来源/机会标识，Aimail 的线程 ID 也保持。
网站来源与来信不凭公司名、邮箱后缀或域名猜测合并。初始一来源一企业档案，关联前企业数不等于已核实的独立法人数量。
同一企业可以有多次询价：每次机会保留自己的负责人、阶段、邮件、停发状态和进展；企业关联不合并发信对象。
当前只在已有可见来源之间导航，还没有跨来源聚合邮件全文。原始邮件和附件仍由 Aimail 保管。

## 业务阶段和逐步建档

| 阶段 | 需要确认的信息 |
| --- | --- |
| 待核验 → 可联系潜客 | 公开来源、联系入口及适合开发的依据；邮箱公开不等于有采购需求 |
| 已首次联系 | 已发送的首封或回复依据，不把创建草稿当成发信 |
| 已建立沟通 | 客户实际回应的依据，不把内部交接当成客户回应 |
| 已确认需求 | 产品、数量/规模、交付国家或地区 |
| 已报价 | 上述需求 + 正式报价/方案引用 |
| 商务 / 技术推进 | 保留报价引用，记录当前待解决事项 |
| 成交 / 转交履约 | 产品、数量、交付地区 + PO/合同/订单引用 |
| 已关闭 / 长期培育 | 关闭或暂缓依据；长期培育仍安排下一次跟进 |

业务阶段允许负责人根据真实证据跳转或纠正，但每次变化必须记录依据。
报价与订单引用只是 CRM 建档，不创建 OA 订单、履约记录或实际报价文件。
除成交/关闭外，保存进展必须有下一步与日期。成交/关闭自动结束本机会的人工跟进，**不会改变 Aimail 发信序列或退订状态**；
停发仍使用既有“停止联系”流程并等待邮件系统回执。

交接状态（待接手、接受、退回）和行动状态（跟进中、等待客户等）分别保留；邮件事件按原事件 ID 幂等登记。
收到事件不会自动宣称需求已确认或交易已成交。旧客户从“待核验”开始；已有行动计划保留为迁移快照。

## 数据与权限合同

本批为 SQLite 增量建表：`company`、`account_company`、`account_workflow`、`account_activity`、
`crawl_attempt`、`crawl_observation`、`crawl_retry`、`worker_status`。不改原账户主键、邮箱、通知或游标。
迁移可重入；旧交接和邮件证据只追加一次，已有表的数据逐项保持。历史缺失不能从审计时间推断。
`account_activity` 与 `crawl_observation` 有拒绝 UPDATE/DELETE 的数据库触发器；当前阶段使用独立的可更新投影。

新增接口沿用现有可信身份头、角色与同源写入校验：

| 接口 | 权限 / 并发控制 |
| --- | --- |
| GET `/api/accounts/{id}/activity?before=` | 管理员或当前负责人/待接手人；不可见记录统一 404；每页 50 条 |
| POST `/api/accounts/{id}/progress` | 仅当前负责人，包括确实负责该机会的管理员；`version` 防止覆盖旧页面，冲突 409 |
| POST `/api/accounts/{id}/company` | 管理员；双方关联版本与核实依据；关联不变更交接/邮件权限 |
| GET `/api/candidates/{id}/attempts` | 管理员 |
| POST `/api/candidates/{id}/retry` | 管理员；最后尝试 ID、失败类别与次数门禁 |

`/api/state` 增加 `accounts[].company`、`accounts[].workflow`；`collection` 只返回给管理员。
旧 `/followup` 路由兼容保留，写入也追加历史并增加版本；旧客户端只修改行动计划，不推断新的业务阶段。
前端轮询不覆盖正在填写的表单；有新版本时保留草稿、禁用保存并要求载入最新记录。
